# Paths and Crowd Simulation

## Overview
Pathfinding operates on an immutable `NavMesh`. A `Simulation` owns its agents and their routes, recalculates a route when a goal is set, and advances agents from a snapshot at each internal substep. Agents are discs for avoidance, while the mesh constrains their centres.

## Requirements

| ID | Type | Description | Acceptance Criteria |
|---|---|---|---|
| SIM-001 | Functional | `find_path` validates endpoints and handles direct paths. | A non-finite endpoint returns `InvalidArgument`; a finite start or goal outside the mesh returns `OutsideMesh`; disconnected containing cells return `NoPath`. If the straight segment is contained in the mesh, the result is exactly `[start, goal]`, except exactly equal (`Vec2::operator==`) endpoints return `[start]`. |
| SIM-002 | Functional | A connected path is a deterministic contained polyline. | It is non-empty, preserves the caller-supplied start and goal as its first and last points when they are not exactly equal, and every segment is contained in the mesh: for every real `t` in `[0,1]`, `start + t * (end - start)` is contained by at least one mesh triangle under MSH-006. Consecutive intermediate points closer than `epsilon` are omitted. Identical input produces exactly equal point sequences on one platform. |
| SIM-003 | Functional | A route crosses only valid mesh adjacency and shortens a corridor through its shared-edge portals. | It does not cut through non-walkable space. A funnel/string-pulling-equivalent result is required rather than returning an unshortened cell-centre route. |
| SIM-004 | Constraint | Route selection is deterministic. | Path length is Euclidean polyline length. Repeated calls with identical finite input on one platform must select the same valid route and return the same point sequence. The winner among effectively equal alternatives is deliberately not prescribed. |
| SIM-005 | Functional | `add_agent` validates configuration and creates a live non-zero id. | Position, radius, max speed, optional goal, and arrival radius must be finite; radius and max speed must be positive. A position or optional goal outside the mesh returns `OutsideMesh`; other invalid configuration returns `InvalidArgument`. A valid optional goal establishes the same initial route/status as `set_goal`; a disconnected goal establishes `NoPath`. |
| SIM-006 | Functional | Arrival radius has one negative sentinel. | `-1.0f` means use the agent radius. Every other negative value, including values less than or greater than `-1.0f`, returns `InvalidArgument`. Zero and positive finite radii are explicit arrival radii. This rule applies to `AgentConfig::arrival_radius` and `set_goal`. |
| SIM-007 | Functional | Goals and goal clearing have defined state transitions. | `set_goal` validates a live id, a finite in-mesh goal, and SIM-006's arrival radius rule. A connected goal farther than its effective arrival radius sets `Moving` with its new route; one already within that radius immediately sets `Reached` and zero velocity. A disconnected in-mesh goal succeeds, sets `NoPath`, and sets velocity to zero. `add_agent` with an optional goal applies these same transitions before it returns. `clear_goal` on a live id clears `AgentState::goal`, discards the route and arrival-radius state, sets velocity to `{0,0}`, and sets status to `Idle`; later `step` calls do not move it until a new goal is set. Unknown or removed ids return `NotFound`. |
| SIM-008 | Functional | `step(seconds)` has explicit validation and motion bounds. | Non-finite or negative duration returns `InvalidArgument` and changes no agent. Zero succeeds and changes no state. A positive duration may be internally subdivided; agents move no faster than `max_speed`, remain contained by the mesh, and do not overshoot a waypoint or goal solely because the duration is large. |
| SIM-009 | Functional | Arrival produces a stable terminal state. | A moving agent becomes `Reached` with zero velocity when its centre is within its effective arrival radius of its goal. An agent without a goal is `Idle`. |
| SIM-010 | Functional | Avoidance uses simultaneous local decisions. | At every internal substep, velocity decisions read a snapshot of all live positions and velocities before updates are applied. When a collision-free local velocity choice exists, nearby discs choose velocities intended to avoid predicted overlap. |
| SIM-011 | Acceptance Criterion | Normal-crowd behavior is required only for small feasible open-space interactions. | In an open convex cell, two initially non-overlapping agents on crossing or overtaking routes choose collision-free local motion when such motion exists, make progress toward their valid goals, and do not overlap by more than `1e-3f` metres after any returned `step`. This is not a promise for arbitrary layouts, densities, or populations. |
| SIM-012 | Constraint | Avoidance is local and deterministic. | It need not implement a named algorithm, globally resolve deadlocks, or guarantee progress in an overfull passage. It must not teleport agents, exceed max speed, produce non-finite state, or move an agent outside the mesh. |
| SIM-013 | Functional | Queries expose snapshots without mutation. | `agent` returns a value snapshot of position, velocity, radius, max speed, goal, and status, or empty for an unknown/removed id. `agent_count` is exact. Neither query changes simulation state. `remove_agent` invalidates its id; all later id-based operations return `NotFound`. |

## Edge Cases
- SIM-001: Endpoint equality is exact `Vec2` equality, whereas containment and segment geometry use `epsilon` under MSH-006.
- SIM-005: `NavMesh::create` cannot create an empty mesh (MSH-005); therefore a `Simulation` is constructed only from a non-empty valid mesh. Adding an agent outside it returns `OutsideMesh`, not `InvalidArgument`.
- SIM-006: `-1.0f` is the sole negative sentinel; `-0.0f` is zero and is valid.
- SIM-008: An invalid `step` is transactional: no position, velocity, status, route, or goal changes.
- SIM-010: Initially overlapping agents may be added when each centre is contained. The implementation must remain finite and attempt separation, but this is robustness behavior and is not covered by SIM-011 acceptance.
